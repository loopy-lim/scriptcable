# 배치 API(batch) 라운드 — 2026-10-25

## 요구

1. **배치 API** — 채터링 문자열 API의 근본 해법: 한 번의 경계로 N 호출. 경계 마샬링 라운드
   (docs/plans/2026-10-25-boundary-marshaling.md)의 후속 과제. AC-3 원문 기준(wasm 30%)을
   추구할 경우에도 이 라운드가 선행.
2. **Node 실런타임 문자열 실측** — 로컬 node 미설치(2026-10-23 재확인)라 CI 몫. 현재 CI 게이트는
   Bun 기준(appendix: bench-gate)이고 Node(V8) 애드온 문자열 수치는 미측정.
3. **provenance** — bun publish 지원 시(조건부). 로컬 bun 1.4.4 `bun publish --help`에
   provenance 플래그 없음(2026-10-25 확인). release.yml 주석이 트리거 문서화 중.

**범위**: 배치 실행기(생성 애드온 C) + JS 와이어 인코더/디코더(core) + 클라이언트·로더
`batch()` 표면 + bench 배치 워크로드 + CI Node 실측 스텝 + 문서. **범위 밖**: wasm 경계 내
배치 루프(scriptc 런타임 변경 — 업스트림 의존), .so 배치 TU(폴백 경로 전용 혜택 대비
안드로이드 version-script·Windows·contract 파장이 큼 — 가정 로그 D6), bench-gate의 Node
베이스라인 대조(러너 노이즈 — 이번 라운드는 기록이 목적).

## 조사 결과 (근거)

- **애드온은 이 저장소 코드젠**(`napi-addon.ts`)이 프로파일별 C를 생성해 코어 아카이브와 링크
  (`buildNodeAddon` — toolchain.ts:440). 실행기가 들어갈 자리가 이미 존재 — 업스트림 변경 불요.
- **싱글 호출 비용 분해**(경계 마샬링 라운드 완료 실측, bun 애드온 repeat 680ns): napi 디스패치
  ~50ns + `napi_get_value_string_utf8` 2-pass + `napi_get_cb_info` + `napi_create_string_utf8`
  + 코어 측 C(alloc/copy ~350ns 추정). 배치는 앞의 napi 항목들을 배치당 1회로 상한하고 코어
  측은 op당 잔존 — 개인당 상한이 코어 측 C + 문자열당 코덱.
- **wasm repeat 1.04µs**: JS 측 제거 가능 ~350ns(이전 라운드에서 이미 제거), 잔여 ~0.9µs는
  wasm 측 scriptc 런타임 alloc/copy — JS 루프 배치로는 소폭(클로저 기계 비용)만 절감. 경계 내
  루프는 scriptc가 생성한 wasm에 실행기를 주입할 방법이 없어 업스트림 의존(외부
  `@scriptc/runtime-wasm32-wasi`).
- **bun:ffi 경로**: 숫자 디스패치 16ns(최적화 후) — 배치 이득 미미. Bun 전달 티어는 마샬링
  export를 이미 애드온으로 티어링(codegen.ts tierMarshaledForBun).
- **Node 측정**: bench-core bench.ts는 bun 전용(build timing 부분). Node는 `node:wasi`·addon
  로드(createRequire) 모두 지원 — 별도 스크립트 + setup-node 스텝이면 실측 가능.
- **테스트 픽스처**: test-fixtures/native.c에 concat(문자열 2→1)·cc(cstring 2→1)·echo(성장
  유발) 상존 — 실행기 통합 테스트가 이를 재사용 가능. napi-addon.test.ts는 소스 문자열
  계약 테스트가 관례; native-loader.test.ts가 테스트 시점 cc 컴파일 관례.

## 설계 결정

1. **D1 실행기는 생성 애드온 C 내부** — `generateNodeAddonSource` 확장. C가 export 시그니처별
   파싱을 프로파일에서 정적 생성(napi 변환·콜백 디스패치를 배치당 1회로 상한).
2. **D2 와이어(LE 가정 — 지원 호스트 전부 LE)**:
   - `meta: Int32Array` = `[count, (exportIdx, argBase) × count]` — argBase는 엔트리 슬롯
     시작 바이트 오프셋.
   - `args: Uint8Array` = 엔트리별 [페이로드(문자열/bytes utf8·raw), 8바이트 정렬 슬롯들].
     슬롯: f64/f32·bool·u8..i32 = f64 비트(setFloat64), i64/u64 = 8바이트 raw,
     string/bytes = (u32 페이로드 오프셋, u32 길이), cstring = (u32 오프셋, u32 길이+NUL 포함).
   - 결과: C가 per-thread grow-only 블록에 엔트리 순서대 기록(숫자 8바이트, 문자열 =
     u32 길이+utf8, cstring = u32 길이(NUL 제외)+utf8, bytes = u32 길이+raw, void = 없음) →
     `napi_create_buffer_copy` 1회 복사로 반환. JS가 레이아웃을 동일 규칙으로 미리 계산하므로
     결과 테이블 불요. 스테디 스테이트 할당 0.
3. **D3 JS 와이어는 core 공용 모듈**(`createBatchWire(profile)`, 새 export `./batch`) — 생성
   클라이언트와 bench-gate가 공유. 코드젠 특화 대신 범용 루프(JS 인코딩은 op당 필수 비용이라
   특화 이득 소소).
4. **D4 유니폼 API** `batch(entries: Array<[name, ...args]>): unknown[]`:
   - 애드온 경로(Node 클라이언트 1순위·Bun 마샬링 티어): 실행기 호출.
   - 부재: 로더(`native-loader`·`wasm-loader`)와 클라이언트의 JS 루프 폴백 — 순차 호출과
     결과 동등, 속도 주장 없음.
5. **D5 wasm 경계 내 배치는 미포함** — 업스트림(scriptc 런타임) 의존. 문서에 명시.
6. **D6 .so 배치 TU 미포함** — ffi 폴백(Windows/koffi)만 혜택인데 파장이 큼(안드로이드
   selective-pulling/version-script, Windows 링크, .so 표면 변화). 후속 제안으로 분리.
7. **D7 실행기 심볼명 `__scriptcable_batch`** — 사용자 export와 충돌하면 코드젠이 실행기를
   생략하고 클라이언트는 `typeof` 검사로 자연 폴백.
8. **D8 CI Node 실측** — bench-core에 Node 측정 스크립트(JS baseline·애드온 ping/add/repeat·
   repeat 배치·koffi fallback 가용 시) 추가, ci.yml에 setup-node@v4 스텝(ubuntu-latest,
   matrix linux에서만) — 결과를 로그 + $GITHUB_STEP_SUMMARY + artifact JSON으로 기록.
   게이트 대조는 노이즈 때문에 미포함(측정 기록 목적).
9. **D9 provenance** — 최신 bun 상태 웹 확인 후: 미지원이면 현행 문서(release.yml 트리거
   주석)로 종결, 지원되면 전환 절차 기록.

## 가정 로그

- **API 형태**: `batch(entries)` 튜플 배열로 결정(call(exportName, ...args) 스타일과 대칭).
  per-export 특화 메서드(`batchRepeat`)는 코드젠 부담 대비 이득 미미 — 기각. 타입은
  `unknown[]`(프로파일별 제네릭 타이핑은 후속).
- **D6 근거**: ffi 배치의 잠재 이득은 폴백 티어 한정(전달 티어는 애드온). 안드로이드 .so는
  selective pulling이라 extra TU가 오브젝트 풀링을 바꿀 수 있음 — 회귀 리스크가 이득 초과.
- **AC-5 수치 기대치 미선언**: 코어 측 C(~350ns/op 추정)가 per-op 하한을 지배 — 개선률은
  측정 후 기록하며, 임계를 미리 못 박지 않음(30% 주장은 업스트림 없인 근거 없음 — 정직 기록).
- **node 부재 재확인(2026-10-25)**: `command -v node` 없음 — AC-6 실측은 CI 푸시 후 확정.

## 잔여 한계 (예상 — 완료 시 실측으로 갱신)

- wasm 배치는 JS 루프 폴백뿐 — 경계 내 실행은 scriptc 런타임 지원 필요(업스트림).
- .so(ffi/koffi) 배치 가속은 미포함 — 폴백 티어는 순차 속도.
- Node 실측 수치는 CI 트리거 전까지 미확정.

## 완료 실측 (2026-10-25)

- **전제 교정 (이번 라운드의 핵심 발견)**: 문자열 배치는 per-op **+8~16% 느리다**(addon repeat
  싱글 762–801ns → 배치 826–926ns/op, 64/배치). 와이어가 napi의 C 변환을 JS 코덱으로 옮길 뿐
  비용 등급이 같고, 절감은 디스패치(~50ns)뿐이라 기계 비용에 흡수된다. per-op 하한은 코어 측
  C(alloc/copy ~0.5–0.67µs) + 문자열당 인코딩/디코딩 — 이 ABI에서 배치가 제거 불가.
  **"배치 API가 문자열 채터링의 근본 해법"이라는 원 요구 전제는 이 ABI에서 반증** — 숫자 위주
  채터링(add −13%: 50 → 43.6ns/op)과 디스패치 절감이 배치의 실제 승리 구간. 문자열은 여전히
  coarse export(한 export 안에서 여러 문자열 처리) 또는 업스트림 scriptc 런타임 개선이 정답.
  BENCHMARK.md §9에 판정 기준 기록.

## G3 리뷰 기록

독립 리뷰어(위임, 새 컨텍스트) 1차 — **FAIL(차단 2건)**. 리뷰어가 18개 적대 프로브·스레드
레이스 프로브·충돌 프로브를 /tmp에서 직접 실행, 문자열 배치 열세 재현(독립 확인)과 함께:

- **F1(P1, 재현) — `__sc_bres_used`가 `_Thread_local` 아님**: dlopen된 .node의 static은
  worker_threads가 공유 — 4 workers × 3000 배치에서 ~95% 손상 + 공유 커서가 타 버퍼 cap을
  넘어 `napi_create_buffer_copy` 힙 overread. **수정**: `_Thread_local` 부여 +
  worker_threads 회귀 테스트(`addon-batch.test.ts` — 4 workers × 1500 배치, 각 워커가
  결정적 체크섬 검증). **변이 검증**: 가드 제거 시 `malloc(): corrupted top size`로 즉시
  크래시(힙 손상 재현) — 복구 시 112 pass/0 fail. 실가드 확인.
- **F2(P2, 재현) — `batch`라는 이름의 export가 실행기와 C 재정의 충돌**: 래퍼 `__sc_<export>`
  실행기 심볼(`__sc_batch`, `__sc_bres_*`, `__sc_bentry_N`)과 충돌 → TU 재정의 에러 →
  소프트-fail로 애드온 전체 소멸(FFI 폴백). **수정**: 코드젠 가드 — 래퍼 이름이 실행기 심볼
  집합·`__sc_bentry_\d+`와 충돌하면 실행기만 생략(사용자 export는 그대로). 소스 계약 테스트
  추가. (export는 모든 C 식별자를 만들 수 있으므로 리네임이 아닌 가드가 완전한 울타리.)
- **F3(P3) — cstring 슬롯 NUL 미검증(방어 심층)**: 위조 슬롯이 strlen으로 args 버퍼 밖까지
  읽을 수 있음. **수정**: `l==0 || args[o+l-1]!=0` → bounds 반환(정상 와이어는 항상 NUL 포함).
- **F4(P3) — bytes 파라미터가 Uint8Array만 받음**: **수정** — ArrayBufferView 전반 허용
  (싱글 애드온 경로와 동등). number[] 등 비뷰는 기존대로 ArrayBuffer 변환.
- **F5(P3) — 폴백 티어 오류 클래스 불일치**: **수정** — `BatchWire.check()` 신설, 생성

  "풀 재사용으로 per-batch 할당이 결과 자체로 축소"로, README는 §9 수치와 정렬.
- **F7(P3, 증거 갭)** — AC-3/4의 관찰 방법이 계획과 다름(로더 테스트 부재·클라이언트 e2e
